# ADR 0008: Stage documents follow arc42, diagrams follow C4, content follows Microsoft

**Status:** Accepted. Stages 1 (discovery) and 2 (solution design) in place, stage 2 with a dynamic view per runtime scenario and a Microsoft reference architecture as its acceptance test; stage 3 follows.

## Context

The four stages (ADR 0007, [DESIGN_STANDARD.md](../DESIGN_STANDARD.md#stages)) were the same layout with a different label, and the specification used headings made up for Teolima. A senior architect would see through both at once: discovery, solution design and technical design are different pieces of work, for different people, with different documents and different diagrams.

Microsoft's guidance says what each piece of work must contain, but not how to structure the documents or which notation to draw. Two open standards that architects already know cover exactly that:

- **arc42**, a template of twelve numbered sections: introduction and goals, constraints, context and scope, solution strategy, building block view, runtime view, deployment view, crosscutting concepts, architecture decisions, quality requirements, risks and technical debt, glossary.
- **C4**, four diagram levels (system context, container, component, code), each at one level of abstraction, with dynamic and deployment views alongside. Microsoft's own diagram guidance uses the same names: context diagram, container diagram, component diagram, deployment diagram.

## Decision

- Each stage owns arc42 sections and one kind of C4 diagram:

  | Stage | arc42 sections | Diagram |
  |---|---|---|
  | 1 Discovery | 1 Introduction and goals, 2 Constraints, 3 Context and scope | System context |
  | 2 Solution design | 4 Solution strategy, 5 Building block view, 6 Runtime view, 9 Architecture decisions | Container, with a dynamic view per key scenario |
  | 3 Technical design | 7 Deployment view, 8 Crosscutting concepts, 10 Quality requirements, 11 Risks and technical debt | Deployment |
  | 4 Compile | Traceability from the package back to every section | The code side of the board |

- The content of each section follows Microsoft's guidance, cited per section in `shared/board/arc42.ts`. Stage 1 follows "Align technical strategy with business requirements": the coach listens, probes, clarifies and evaluates, and the result is the functional specification that page names as the expected outcome of discovery.
- A stage document is a list of items in sections. Each section accepts only its own item types (a stakeholder has a role, a quality goal its attribute, a constraint its category), so the documents stay structured enough for the compiler to read.
- Stage 2 traces back to stage 1 by id. Every building block names the specification items it serves; every runtime scenario names the user flow it realises; every quality approach names its quality goal; a decision may name the rule it settles. The gate refuses approval while a user flow has no scenario, an oversight rule has no approval or decision, an external system has no tool or knowledge source, or an agent serves nothing. Section 5 is derived from the board and section 6 from the scenarios, so the document and the diagram cannot disagree.
- A decision record (arc42 section 9) is structured: its topic, the options weighed, the option chosen as its name, and the consequences. Platform, complexity, hosting and, for several agents, the orchestration pattern are required, each linked to the Microsoft guidance for that question.
- The user edits the document directly: adds items, edits them inline, removes them, and adds sections of their own. What the coach records quotes its source; what the user types is marked as theirs.
- Every Microsoft link the code and the design standard cite is checked against the guidance snapshot in the tests, so a page Microsoft moves breaks the build instead of the advice. The first run of that check found two Cloud Adoption Framework pages that had been restructured away; their claims now cite the pages that hold them today.

## Consequences

- Each stage produces a document a reviewer recognises, in an order they know, with a source behind every line.
- The compiler reads structured sections instead of free text: quality goals become quality scenarios and pillar checks, constraints become deployment parameters, the business context becomes the system's external interfaces.
- The diagrams can be held to C4's rules: the context diagram shows no internals, and the container diagram of stage 2 shows no deployment topology. The container diagram keeps the context diagram's people and external systems, placed next to the blocks that serve them, so the reader sees the same neighbours one level deeper.
- The compiler can trace every resource it generates to a line in the specification, and the trace is part of the exported document (section 5, "Traceability").
- arc42 and C4 are credited where they are used; Teolima does not copy their text.
